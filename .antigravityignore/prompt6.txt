Mejora de Razonamiento y Lógica de Juego para Modelos Pequeños (SLMs)
Contexto del Problema: Estamos detectando problemas de rendimiento cuando utilizamos modelos pequeños (como Gemma 3 o Llama 3 8B) en el rol de "Jugador". Estos modelos tienden a entrar en bucles cognitivos: repiten preguntas que ya han hecho, olvidan respuestas anteriores o realizan preguntas sin sentido lógico. Además, el "Maestro" a veces genera historias demasiado abstractas o complejas para que estos modelos pequeños las deduzcan.

Objetivo: Implementar una estrategia de "Cadena de Pensamiento Forzada" (Chain of Thought - CoT) para el Jugador y una Simplificación Lógica para el Maestro. Queremos obligar al Jugador a "pensar antes de hablar" y asegurarnos de que el código Python gestione ese pensamiento para no confundir al Maestro.

Tareas de Refactorización
1. Ajuste de Dificultad del Maestro (prompts/maestro_fase1_gen.txt)
Modifica el prompt de generación de historias (Fase 1) para reducir la complejidad abstracta.

Añade instrucciones explícitas para que las historias generadas sean de dificultad intermedia-baja.

Restringe la temática: deben basarse estrictamente en causa y efecto lógicos. Prohíbe explicaciones basadas en magia, ciencia ficción compleja o coincidencias emocionales abstractas.

Exige que el acertijo inicial contenga al menos una pista visual clara que oriente al jugador hacia la solución física del problema.

2. Implementación de "Pensamiento Visible" en el Jugador (prompts/jugador.txt)
Modifica el prompt del Jugador para cambiar su estructura de respuesta. Ya no debe responder directamente con la pregunta.

Instruye al modelo para que realice un análisis previo antes de formular la pregunta. Debe revisar explícitamente su historial para evitar duplicados y formular una hipótesis.

Establece un formato de salida estricto usando etiquetas personalizadas (estilo XML). La respuesta debe tener dos bloques diferenciados:

Un bloque de PENSAMIENTO (donde analiza y planea).

Un bloque de PREGUNTA (donde escribe únicamente la pregunta final o la solución).

3. Adaptación del Parser en GameManager (game_manager.py)
El cambio en el prompt del Jugador romperá el flujo actual si no adaptamos el código, ya que el Maestro recibiría todo el texto (incluyendo el pensamiento interno), lo cual lo confundirá.

Debes modificar la lógica dentro del bucle principal del juego (start_game):

Intercepción: Captura la respuesta cruda del modelo Jugador.

Parsing: Implementa una lógica (puedes usar expresiones regulares) para extraer exclusivamente el contenido que está dentro de las etiquetas de PREGUNTA que definiste en el paso anterior.

Enrutamiento:

Muestra por consola el pensamiento (para que el usuario vea el razonamiento).

Pasa solo el contenido limpio de la pregunta al método _get_master_response y a la validación de solución final (startswith("Respuesta:")).

Fallback: Asegúrate de que, si el modelo olvida poner las etiquetas (lo cual puede pasar), el sistema tenga un plan de respaldo para usar la respuesta completa como pregunta.

Resultado Esperado: El Jugador ahora "reflexionará" en voz alta, reduciendo las alucinaciones y repeticiones. El código Python actuará como filtro, asegurando que el Maestro solo reciba la pregunta limpia, manteniendo la integridad del juego "Sí/No".
