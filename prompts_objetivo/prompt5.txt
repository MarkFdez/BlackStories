Contexto Crítico: Estamos enfrentando problemas con modelos pequeños (como Gemma 3) que se confunden al recibir un System Prompt demasiado complejo con múltiples instrucciones. Para solucionar esto, vamos a cambiar de un enfoque de "Prompt Único" a una arquitectura de "Prompts Dinámicos por Fases". Además, para facilitar el uso, vamos a eliminar la configuración manual de archivos por CLI y pasar a un sistema de convención de archivos.

Objetivo Global: Refactorizar la aplicación para que cargue automáticamente 4 prompts específicos (3 para las fases del Maestro, 1 para el Jugador) desde una carpeta prompts/ y los inyecte dinámicamente en cada llamada a la API según el estado del juego.

Instrucciones de Implementación Paso a Paso
1. Reestructuración de Archivos (prompts/)
Analiza el archivo actual prompts/maestro_prompt.txt y divide su lógica en tres archivos nuevos. Asegúrate de que exista también el del jugador. La carpeta prompts/ debe quedar así:

prompts/maestro_fase1_gen.txt: Extrae aquí SOLO la lógica de la Fase 1. Debe contener las instrucciones para generar la historia y el formato JSON.

prompts/maestro_fase2_juez.txt: Extrae aquí SOLO la lógica de la Fase 2. Debe contener las instrucciones estrictas para responder "Sí/No/No relevante" y prohibir el JSON.

prompts/maestro_fase3_eval.txt: Extrae aquí SOLO la lógica de la Fase 3. Debe contener las instrucciones para el veredicto final.

prompts/jugador.txt: Asegúrate de que el prompt del jugador esté en este archivo (renómbralo si es necesario).

2. Actualización de la Interfaz de Proveedores (providers/)
Necesitamos que los proveedores admitan cambiar su personalidad al vuelo.

Modifica la firma del método generate_response en la clase base y en las implementaciones (ej: OllamaProvider, GeminiProvider, etc.).

Añade un parámetro opcional: system_prompt=None (o system_instruction).

Lógica: Si system_prompt tiene valor, el proveedor debe usar este texto como instrucción de sistema para esa generación específica, ignorando el prompt con el que se inicializó.

3. Refactorización de main.py (Entrada y Carga)
Elimina la complejidad de la línea de comandos y carga los archivos automáticamente.

Argumentos CLI: Elimina los argumentos obligatorios -c1 (--character1) y -c2 (--character2). Mantén solo los selectores de modelo (-p1, -m1, etc.).

Lógica de Carga: Implementa una función que lea el contenido de texto de los 4 archivos obligatorios mencionados en el punto 1.

Validación: Si falta alguno de los 4 archivos en la carpeta prompts/, lanza un error y detén la ejecución.

Instanciación: Pasa el contenido de estos 4 textos al constructor de GameManager.

4. Refactorización de GameManager (Lógica de Fases)
Actualiza el gestor para usar los prompts dinámicos.

__init__: Actualiza el constructor para recibir los 4 textos de los prompts. Guárdalos en variables separadas:

self.prompt_master_gen

self.prompt_master_judge

self.prompt_master_eval

self.prompt_player (Si el jugador es estático, puedes pasarlo al inicializar el modelo del jugador).

Inyección Dinámica:

En _initialize_story: Llama a generate_response pasando system_prompt=self.prompt_master_gen.

En _get_master_response: Llama a generate_response pasando system_prompt=self.prompt_master_judge.

En _handle_final_solution: Llama a generate_response pasando system_prompt=self.prompt_master_eval.

Resultado Final Esperado: El usuario ejecuta uv run main.py -p1 ollama ... sin especificar archivos. El sistema carga los prompts, y cuando el Maestro tiene que responder "Sí/No", recibe exclusivamente las instrucciones de juez, eliminando cualquier posibilidad de que alucine un JSON por contaminación de contexto.
